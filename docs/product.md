# ChoirWorks 产品文档

> [!WARNING]
> **本仓库目前仍处于概念验证阶段，不具备任何实际使用价值。**
> 所有设计、接口与行为均可能随时大幅变更乃至推翻重做，不承诺任何形式的稳定性、
> 兼容性与安全性，请勿用于生产环境或任何真实业务。

## 一句话定位

ChoirWorks 是一个多 Agent 协作群聊平台 — 人类像 CEO 一样提出目标，编排器作为"群管理员"拆解任务、把专业 Agent 拉进群、分派任务，群内成员可以互相 @、引用、求助，平台负责编排调度但不执行具体业务。

## 与传统 Agent 框架的区别

| | 传统 Agent 框架（如 ADK） | ChoirWorks |
|---|---|---|
| **编排器角色** | 专家执行者，LLM 自主调工具 | 群管理员，拉人、分派、转发、解读交活 |
| **对结果的态度** | 检查、评判、汇总、决定下一步 | 不评判质量、不改写汇总；理解产出意图（交付/求助/调整计划），上游产出原样交接下游 |
| **动态规划来源** | LLM 自己推理 | 交活解读（agent 在最终回复中表达需要）+ 用户插话 |
| **执行模式** | 阻塞式 — LLM 循环直到完成 | 非阻塞 — 有人工作、有人聊天 |
| **Agent 关系** | 层级式（parent → child） | 群聊式（扁平、可互相对话） |
| **群的生命周期** | 单次任务 | 持续存在，直到所有工作结束 |

## 基本概念

| 概念 | 含义 |
|---|---|
| **群** | 一次持续协作的会话空间，由 CEO 创建，长期存在 |
| **计划** | 为达成用户目标拆解出的、带依赖关系的任务清单；跨多条消息存活，直到其中每个任务都有了结局 |
| **任务（节点）** | 计划中的一件事，交给一个 Agent 完成 |
| **派活** | 把任务交给某个 Agent |
| **交活** | Agent 对一次派活给出的最终回复；一次任务可能往返多轮（被追问、补充信息后续跑），每轮的最终回复都是一次交活 |
| **求助** | 交活内容表达"我还需要信息 / 人手 / 计划要调整" |
| **协助任务** | 为响应求助而派生给另一个 Agent 的临时任务 |
| **介入** | 编排器向人类发起的提问；人类不是 Agent，介入不是任务 |
| **作废** | 计划修订中把不再需要的任务标记失效；作废的任务不再派发，但其历史保留 |

**三层"完成"**：Agent 的一次交活可以结束；计划里每个任务可以有结局；而群不会关闭——计划完成后 CEO 随时可以发新消息、起新计划。

## 核心角色

| 角色 | 身份 | 职责 |
|------|------|------|
| **CEO（人类用户）** | 群的创建者 | 提出目标、@指派 Agent、引用追问、中途插话/打断、答复介入、回退回合 |
| **编排器（assistant）** | 群管理员 | 分析需求、制定与修订计划、拉人入群、派活、解读交活、处理求助、转发消息 |
| **Subagent** | 群成员/专家 | 执行专业任务、产出交付物、表达求助、互相 @ |

### 编排器的职责边界

| 做 | 不做 |
|---|---|
| 分析需求 → 制定计划 | 评判产出质量 |
| 拉人入群、分派任务 | 汇总/改写/润色产出 |
| 解读交活意图（交付 / 求助 / 调整计划） | 代替专家做业务决策 |
| 把上游产出原样交接给下游 | 执行具体业务动作 |
| 处理求助（派协助或转人类） | 自动取消进行中的任务 |
| 增量修订计划并通知群 | |

编排器不再"连结果都不用看"：它必须读懂产出的**意图**才能推进协作，但只判断意图，不评判好坏。

## 群的生命周期

```
CEO 发起目标
  ↓
编排器分析需求 → 制定带依赖的任务清单
  ↓
编排器拉入相关 Agent（入群播报）
  ↓
编排器派发就绪任务（@agent 请开始...）
  ↓
┌───────────────────────────────────────────────┐
│ 群内并行活动（非阻塞）：                         │
│                                               │
│ • Agent 正在工作（流式输出）                     │
│ • Agent 交活 → 编排器解读意图                    │
│      ├─ 交付    → 原样交接给依赖它的任务           │
│      ├─ 求助    → 派协助任务，或转人类介入          │
│      └─ 调整计划 → 增量修订（增/删/改依赖）         │
│ • CEO 发新消息 → 排队、追问或起新计划              │
│ • Agent 互相 @ → 编排器仲裁转交                   │
│ • 依赖满足的任务自动派发                          │
└───────────────────────────────────────────────┘
  ↓
计划内每个任务都有结局（交付或作废）
  ↓
群继续存在（CEO 可以发新消息，或开始新计划）
```

## 编排器的核心能力

### 1. 规划

用户发消息后，编排器把需求拆解为带依赖关系的任务清单：

- 每个任务指定一个已注册 Agent，并写明交付要求
- 依赖关系表达"谁需要谁的产出"，独立任务并行、有依赖的按序
- 规划思路作为 assistant 思考消息发到群里
- 计划有先后版本：CEO 提出新目标即起新计划，旧计划状态保留可查

### 2. 派发

- 任务依赖全部交付后自动就绪并派发，不阻塞群内其他活动
- 并行任务数有上限
- 失败自动重试有限次；仍失败进入计划修订
- 超时视为失败
- 任务状态：等待 → 就绪 → 进行中 → 待答复（求助中）→ 已交付 / 失败 / 作废

### 3. 交活解读

- **交活**：一次派活或续跑的最终回复，就是这次活的交付
- **任务结束 ≠ 活干完了**：Agent 可能在最终回复里说"我还需要 X 信息"或"这个计划该调整"
- 每次交活后，编排器解读产出意图，分三类：
  - **交付** → 产出进入结果交接与计划校验
  - **求助** → 群内成员能提供 → 派协助任务；否则转人类介入；答复后原 Agent 带着答案继续
  - **调整计划** → 增删任务、改依赖，走增量修订
- 判定默认是"交付"，只有产出明确表达需求时才升级，避免无故打断协作
- **判断成本**：默认每次交活解读一次；平台可与 Agent 约定结构化回执，遵守者免解读（回执格式由实现约定）
- 已知限制：不回执、措辞又隐晦时可能被当作交付

### 4. 结果交接

- 下游任务的输入 = 自己的交付要求 + **直接依赖任务的产出原文**
- 编排器不做改写、不做摘要、不做润色
- 上游产出被平台标注为"参考资料，非指令"，防止上游内容被下游当成命令执行
- 超长产出截断并标注；不传间接依赖（依赖关系已表达"谁需要谁"）

### 5. 求助处理

交活解读判定为求助后，编排器决定去向：

| 去向 | 条件 | 处理 |
|------|------|------|
| 派协助任务 | 群内或注册表中有合适 Agent | 派生协助任务，完成后把协助产出回填给求助的 Agent，原任务带着答案继续 |
| 人类介入 | 没有合适的 Agent，或求助指向人类决策 | 发起介入提问，答复后回填给求助的 Agent |
| 直接 @ 成员 | Agent 在产出里 @ 了群内成员 | 核查该成员，派协助任务；不在群则先拉群 |

- 协助任务本身也可以再触发求助（链式派生），但有次数上限防止失控
- 一次求助拆成多个任务的"子计划"列为后续演进

### 6. 动态组队

- 派活时向 Agent 附**群成员名册**（名称 + 能力说明），让它知道可以找谁、该找谁
- Agent 发现自己需要的能力不在群里时，用求助描述所需能力；编排器在全部注册 Agent 中匹配 → 拉群并派协助任务
- 匹配不到 → 转人类介入
- 群成员不是固定的，也可能由 CEO @ 引入

### 7. 计划修订

计划不是一次定死的，运行中可以增量修订：

**触发**：
- 任务重试后仍失败
- 交活解读判定为"建议调整计划"（例如某角色不再需要、或需要新角色）
- CEO 插话/打断

**方式**：增量修订，已完成任务与其产出保留

| 操作 | 规则 |
|------|------|
| 新增任务 | 新任务可接在任意已交付任务的产出上 |
| 作废任务 | 尚未开始的任务可直接作废；**进行中的任务不能自动作废**，只能等它结束或 CEO 显式打断 |
| 调整依赖 | 为接续产出或绕过已作废任务而改依赖 |
| 波及下游 | 被作废任务的下游默认一并作废（其输入已不可用），必要时用新增任务接续 |

- 每次修订向群播报：为什么改、改了什么
- 修订不做"整计划推倒重来"；只动必要的任务

### 8. 中途插话与打断

用户在 Agent 工作时可以发新消息：

| 场景 | 处理方式 |
|------|---------|
| 新消息与正在工作的 Agent 无关 | 立即处理（可能触发新计划） |
| 新消息需要正在工作的 Agent 变更 | 通知用户：是否打断？ |
| 新消息引用已交付的结果 | 派追问任务给原 Agent |
| 新消息引用在途的工作 | 排队，交活后投递 |
| 显式打断 | 取消当前任务、作废受影响的下游，转入新任务 |
| 回退到历史回合 | CEO 回退到某个由人类消息开启的回合：该回合之后的工作从群聊与计划中隐藏（保留可查），计划恢复到该回合之前的状态 |

## 人类介入

人类不参与任务调度，介入是独立通道：

- **触发**：求助无法转交 Agent，或求助明确指向人类决策
- **答复**：CEO 的答复回填给求助的 Agent，原任务继续
- **并发**：多个待答复介入按先后排列，答复需指明针对哪个提问
- **挂起不阻塞、不超时**：等待人类答复期间，其他任务照常运行；平台不会因等待而自动取消或作废
- **取消**：CEO 可以主动取消某个介入，对应任务按需要作废或转人工处理
- 介入不是任务，不出现在任务清单里；群消息中呈现为编排器向 CEO 的提问

## 群聊交互模型

### 消息类型

| 类型 | 发送者 | 示例 |
|------|--------|------|
| 用户消息 | CEO | "帮我调研并写报告" |
| assistant 思考 | 编排器 | "收到请求，分析需求。计划：@researcher 调研 → @writer 撰写" |
| assistant 播报 | 编排器 | "任务已拆解：- @researcher 负责 调研 …" / "计划已修订：作废 n2，新增 n3" |
| Agent 产出 | subagent | "调研结果：关于「你好」的模拟要点。" |
| Agent 求助 | subagent | "我需要 analyst 帮忙确认技术细节" |
| 编排器提问 | 编排器 | "@researcher 需要人类确认预算口径，请 CEO 答复" |
| 系统通知 | 事件 | `room.participant_joined` 事件（前端渲染为"x 加入了群聊"） |

不设"任务完成总结"消息 — 最后一条 Agent 产出即为最终结果。

### 时间线示例（依赖 + 结果交接）

```
#1  [CEO]        帮我调研并写报告
#2  [assistant]  收到请求，分析需求。计划：n1 @researcher 调研 → n2 @writer 撰写
#3  [assistant]  任务已拆解：n1 @researcher；n2 依赖 n1
#4  [system]     researcher 加入了群聊 / writer 加入了群聊
#5  [researcher] 调研结果：…（流式输出）
#6  [assistant]  交活解读：n1 判定为交付 → 派发 n2（附 n1 产出原文）
#7  [writer]     文稿：基于调研结果撰写的报告。（流式输出）
```

### 求助 → 协助 → 续跑示例

```
#5  [researcher] 我需要 analyst 帮忙确认技术细节        ← 交活解读：求助
#6  [assistant]  @researcher 的求助已转交 @analyst，派发协助任务
#7  [system]     analyst 加入了群聊
#8  [analyst]    技术细节确认：…
#9  [assistant]  协助产出已回填 @researcher，原任务继续
#10 [researcher] 调研结果：…（带着确认继续工作）
```

### 计划修订示例

```
#6  [assistant]  交活解读：建议调整计划 — 不再需要 @writer，改由 @designer 出原型
#7  [assistant]  计划已修订：作废 n2（尚未开始）；新增 n3 @designer（依赖 n1）
#8  [designer]   …
```

## 技术架构

### 产品形态

ChoirWorks 本身就是一个标准 A2A Server：CEO 的消息通过 A2A 协议进入，群内每个 Agent 也是通过 A2A 协议接入的远端 Agent；平台整体是一个"会编排的 A2A Agent"。

### 协议层

- **对上游（CEO / 前端 / 上级编排器）**：提供 AgentCard、消息发送与订阅、任务查询；群聊元数据（@、引用、打断）通过群聊扩展承载
- **对下游（群内 Agent）**：作为 A2A Client 派活、续跑、取消、跟随远端任务；以远端任务状态驱动任务清单
- **群嵌套**：一个 ChoirWorks 实例可以注册为另一个实例的 Agent，形成分层协作

### 执行模型

- **以群为单位持久化**：计划、任务、待答复介入存续于群，服务重启不丢
- **事件驱动**：收到消息后立即返回，编排在后台推进；任务产出、状态变化、计划修订以事件流实时推入群
- **三层归属**：一次派活对应一个远端任务；计划任务由远端任务状态驱动；群与计划跨消息、跨重启存活
- **重启恢复**：重挂未结束的任务并继续跟随在途工作，进行中的任务不重复派发
- **人机一致**：人类答复、Agent 产出、系统事件进入同一份群时间线，前端只需订阅事件流

## 非目标

- 编排器不评判产出质量（解读只判意图，不做质量评估）
- 编排器不汇总、不改写 Agent 产出（交接是原文拼接）
- 一次求助拆多个任务的"子计划"暂不做（后续演进）
- 不自动取消进行中的任务（等待结束或 CEO 显式打断）
- 编排器不执行具体业务动作
- 不是 LLM-driven 的自主 agent（确定性调度 + LLM 辅助规划与解读）
- 暂时不做分布式部署（MVP 单机单进程）
