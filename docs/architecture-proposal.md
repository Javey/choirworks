# ChoirWorks 需求驱动架构提案

日期：2026-09-20

状态：待确认的独立设计提案，不代表现有实现，也不自动授权重写项目。

需求依据：[产品文档](product.md)。本提案不受现有代码结构约束；已废弃的 [Room Extension v1](extensions/room-v1.md) 不作为设计依据。产品语义仍以产品文档为准，新增的实现选择与待决策边界在本文说明。

## 1. 核心定位

ChoirWorks 是一个持久化的协作调度系统，以群聊为交互界面，以 A2A 为接入协议，LLM 只提供规划与意图判断。

不是让一个大 Agent 循环调用其他 Agent，而是让确定性的系统管理工作，仅在需要理解语言的环节使用 LLM。

保留以下产品边界：

- 编排器不执行业务，不评判质量，不汇总、改写或润色 Agent 产出。
- 直接依赖的产出按原文交接，标记为参考资料而非指令；超长截断并说明。
- 不自动取消进行中的任务；人类等待不自动超时。
- 群持续存在，计划和工作跨消息、跨重启存活。
- MVP 单机单进程，不提前拆分微服务或引入外部消息队列。

## 2. 领域模型与生命周期

| 概念 | 职责 | 生命周期 |
|---|---|---|
| 群 Conversation | 成员、消息、计划、介入的归属 | 不随任务结束而关闭 |
| 回合 Turn | 一条人类消息及其引发的操作，提供回退边界 | 消息被处理不代表相关工作结束 |
| 计划 Plan | 某个目标的任务图及修订记录 | 所有工作结算；成功与失败分别表达 |
| 工作项 WorkItem | 业务上要完成的一件事 | 交付、作废等明确结局 |
| 执行记录 Execution | 一次具体的远端派发与跟随 | 远端执行结束 |
| 介入 Intervention | 需要人类定向回答的问题 | 答复、主动取消或失效 |

工作项不等于远端 A2A Task。例如，调研 Agent 的远端任务完成，但交活内容为“缺少预算信息”：本次执行结束，调研工作项仍在等待答复。人类回答后工作项继续；远端任务能否续用由协议适配层判断，不能续用则建立新的执行记录。

新目标可以创建新计划，不覆盖仍在运行的旧计划。计划的业务完成与某一次上游协议请求的完成分开定义。

## 3. 模块化单体

```text
群聊前端 / 上级 ChoirWorks
            │
      A2A 接入与群聊扩展
            │
        协作命令入口
            │
     会话级状态机 ───── LLM 决策服务
            │           规划 / 意图 / 修订建议
            │
    数据库：状态 + 时间线 + 待执行动作
            │
        后台执行器
            │
        A2A 远端适配
            │
         专业 Agent
```

| 模块 | 职责 |
|---|---|
| 协作领域 | 计划、依赖、介入、修订、回退规则 |
| 应用层 | 处理消息与命令，组织一次状态变更 |
| 执行层 | 派发、跟随、重试、取消、恢复 |
| 协议层 | A2A 输入输出与领域对象之间的转换 |
| 存储层 | 事务、查询、迁移和持久化事件 |

领域层不依赖 HTTP、SDK 事件队列或前端消息格式。对外仍是标准 A2A Server；群级游标、定向答复等能力通过明确的扩展表达，不把持续存在的群伪装成永不结束的任务。扩展的具体字段和兼容策略在协议设计阶段确认。

## 4. 短状态变更与异步动作

所有输入转换成明确命令，例如提交目标、收到远端交活、回答介入、应用计划补丁、确认取消、回退回合。

同一群内的状态修改串行处理，不同群之间并行；远端执行与模型调用不占用会话状态锁。

一次处理流程：

1. 接收命令，校验当前状态。
2. 在短事务内更新状态、记录事件、登记后续动作。
3. 提交后立即返回。
4. 后台执行模型调用或远端请求。
5. 结果作为新命令回到会话。

模型调用期间计划可能已改变，模型结果应携带所依据的计划版本。应用前重新校验，不能把过期建议直接覆盖到新状态。

## 5. LLM 提建议，确定性规则决定执行

| 能力 | 输入 | 输出 |
|---|---|---|
| 规划与路由 | 用户目标、当前工作、Agent 能力 | 新计划或明确的消息处理建议 |
| 交活解读 | Agent 最终回复、必要上下文 | 交付 / 求助 / 建议修订 |
| 修订建议 | 失败原因或新要求、现有计划 | 增量补丁 |

输出使用明确的结构化类型，由代码检查：Agent 与依赖是否存在、是否形成环、是否修改已交付工作、是否涉及未经确认的在途取消、是否超过协助派生和重试限制。

LLM 无权直接修改数据库或取消任务。结构化回执可跳过交活解读；没有明确需求时默认交付。用户看到简短的计划依据和操作说明，不需要暴露模型内部推理过程。

## 6. 持久化与恢复

从第一阶段保存三类数据：

- 业务状态：群、计划、工作项、执行、介入、排队消息。
- 持久化时间线：消息、状态变化、修订记录、产物引用。
- 待执行动作：已经决定、尚未可靠完成的派发、取消等动作。

一次业务变更在同一事务中提交状态、事件和待执行动作。后台执行器从数据库领取动作，避免已接受的操作因进程退出而丢失。MVP 可使用 SQLite，无需额外消息队列。

### 远端执行的保证边界

如果远端已收到派发，本地却在保存远端任务 ID 前崩溃，仅靠本地事务无法保证不重复执行。

因此需要稳定的派发标识，以及远端去重或查询约定。远端不支持时，恢复后应标为“派发结果待确认”，而不是盲目重发。不得宣称仅凭本地动作表就实现端到端恰好执行一次。

已知远端任务应重新查询或订阅跟随，不能因为本地重启就重新派发。协议兼容性与未知派发结果的用户处理方式需要专门验收。

## 7. 实时与历史共用时间线

每个群的持久化事件具有以下信息：

```text
event_id、conversation_id、seq、turn_id、
plan_id / work_item_id、type、schema_version、payload
```

前端只维护一个事件归并器：历史加载从指定序号读取，实时订阅继续接收，断线从最后确认的序号补读，重复事件按标识去重。

不分别维护实时消息生成与历史消息重新推断两套逻辑。流式文本可合并分块保存，不必每个 token 写库；最终原文产物与业务状态必须可靠落盘。

下游引用明确的产物版本，只接收直接依赖原文。传递内容标注为参考资料，超长截断并说明，不以摘要替代原文。

## 8. 复杂交互的显式操作

### 人工介入

回答关联 `intervention_id`。多个问题待答时，普通聊天不能自动回答第一条。等待不占执行槽，没有自动超时；取消由用户显式操作。

### 计划修订

补丁绑定计划版本，一次校验、原子应用，保留已交付工作及历史。涉及在途工作先生成取消确认，不能先作废再询问；目标提前结束则确认失效。

### 引用与排队

引用指向稳定的消息、产物或工作项 ID。引用在途工作时保存待投递记录，交活后处理，不依赖仅存于内存的回调。

### 回退

回退实现为切换当前可见历史并恢复计划快照，不删除旧记录。

隐藏历史不能撤销远端已经产生的业务副作用。建议默认有在途工作时先等待，或由用户明确确认取消后再回退；旧执行迟到的结果保留在旧历史，不得污染恢复后的计划。

这是一项待确认的产品边界，不是产品文档已确定的全部回退细则。计划结算、快照范围、远端无法确认取消时的处理，也需在实施前明确。

## 9. 开发与验收顺序

按完整协作链路交付，而非先写完所有接口再拼装业务。

| 阶段 | 可验收闭环 |
|---|---|
| 1. 最小闭环 | 注册 Agent → 人类发目标 → 派一个工作 → 流式产出 → 刷新仍可见 |
| 2. 可靠执行 | 持久化派发、重启跟随、去重与异常恢复 |
| 3. 任务图 | 并行、依赖、原文交接、有限重试 |
| 4. 求助闭环 | 交活解读 → 人类或 Agent 协助 → 原工作续跑 |
| 5. 动态协作 | 多计划、插话、引用排队、增量修订、取消确认 |
| 6. 历史与组合 | 回退、嵌套 ChoirWorks、完整协议验收 |

每阶段除正常流程，还需验证重复输入、断线、崩溃、交错到达和恢复后状态一致性。每个功能点完成后交用户确认，再继续后续功能。

## 10. 设计结论

把复杂度放在明确的数据模型和状态机里，让协议、模型和界面围绕它工作。

核心验收标准不是编排器有多聪明，而是人在聊天、Agent 在工作、服务发生重启时，每件事仍归属清楚、可恢复、不会被静默丢掉。
